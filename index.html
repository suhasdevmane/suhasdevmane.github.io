Why OntoSage

Grounded answers, any stakeholder, any building.

One natural-language interface over a single building's own data — built so every answer traces back to a real triple or row.

🎯

Grounded, never fabricated

Every figure traces to live data — the graph, the database, or the floor plan. If it isn't there, OntoSage says so.

🧩

Agentic & multi-intent

A LangGraph state machine decomposes a question and routes each part to the right agent, then fuses one answer.

💬

Zero-knowledge to expert

Lay terms resolve ("stuffy" → CO₂) for anyone; experts still get Brick classes and the SPARQL browser.

🏢

Building-agnostic

Onboard any building from the admin console — identity, ontology, sensors, documents, floor plans. No code change.

🔒

Admin-controlled access

Every data endpoint is gated by RBAC — 6 roles × 20 permissions. Personas frame answers; they never grant access.

⚙️

Local or API models

Run fully local on Ollama (gpt-oss:20b) or via OpenAI — model and embeddings switch independently.

How it works

Connect data → get answers.

A question is answerable when the sensor is a triple in the graph and its readings are rows in a registered database. Onboarding is drop-in — no code.

Connect the building

Drop a Brick/BACnet TTL and register the database from the admin console. Both halves link via ref:storedAt.

Ask in plain English

Dialogue classifies intent, rewrites follow-ups, and routes through SPARQL → SQL → analytics / floor-plan agents.

Get a grounded answer

Values are computed live and framed for the asker — facility manager, occupant, researcher, or executive.
